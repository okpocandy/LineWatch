# LineWatch 작업 체크리스트

작품의 범위는 [기획안](Starter_Portfolio_Plan.md)에 정의한다. 이 문서는 구현 순서와 작업별 완료 기준이다. 작성 기준: 2026-11-11.

## 새 대화 인수인계

마지막 갱신: **2026-11-15, FANUC LW-07D ③ 실제 목표 100개 도착·실패/중단·SCARA 회귀 검증 완료, 다음 LW-08**. 이동/정지 UI 안내 뒤 사용자 다음 진행 승인을 반영했다. 개별 버튼별 수동 수치는 별도 보고되지 않았다. 새 대화에서는 이 절과 아래 누적 이력을 먼저 읽는다. 이전 Starter 연결 완료 기록은 당시의 검증 이력이며 현재 구조는 이 절을 따른다. 최종 포트폴리오도 누적 이력과 실제 결과를 함께 확인한다.

### 현재 상태와 이어갈 위치

- 실제 Unity 프로젝트는 `D:\Unity_study\LineWatch`다. 대화의 현재 작업 폴더가 다른 곳이어도 이 경로를 대상으로 한다. Unity CLI 호출에는 해당 `--project-path`를 명시한다.
- Unity 6000.3.21f1 / URP 17.3.0 / realvirtual Starter 6.3.6 / Both 입력을 사용한다. 이미 끝낸 설치·제공 데모 검증은 반복하지 않는다. Urban 에셋은 사용하지 않는다.
- **LW-01~07의 기존 완료 후 경로 제어 개선의 구현·자동 검증과 새 모드 UI의 사용자 직접 확인을 마쳤다.** 기존 5mm·1°·15° 필터·수락 목표 캐시는 제거했다. 기본 관절 이동은 큰 회전을 허용하고 동기 도착하며, 직선 작업 이동은 분기·회전 범위와 중간 경로를 검증해 같은 경로를 실행한다. 186개 끝점에서 관절 모드 거절 0·직선 모드 거절 20, 실제 직선 최대 이탈 약 0.0164mm, 실제 100개 목표·FANUC 회귀가 통과했다. 후속 FANUC LW-07A~07B도 아래와 같이 완료했고 다음 구현은 LW-07C다.
- **FANUC LW-07A·LW-07B 완료:** 홈 기하·순수 FK·현재값 진단과 사용자 확인 후 100개 자세×3배치×4도구 TCP의 1,200개 정적 대조를 통과했다. 최대 로컬 위치 차이는 약 0.00065mm·전체 회전 차이는 약 0.000027°다. 실제 API 목표 4개(홈 포함)·진단 표본 163개·중간 정지 유지도 통과했다. 과정 ③은 검증 도구·문서만 추가/갱신했고 런타임 코드·UI·씬·프리팹·설정은 유지했다. 후속 LW-07C의 현재 진행은 아래와 같다.
- **FANUC LW-07C 완료:** 순수 IK 기준 검증 후 목표 100개·초기값 3개·총 240회/50ms를 고정해 전체 수렴을 확인했다. 단독은 277/300, 기본 묶음 목표 100/100·3배치×4도구 1,200/1,200 성공이다. 최대 모델 차이는 약 0.0991mm·0.0235°로 기준 이내고 실패·초기값 대체·시간을 따로 기록했다. C③에서는 솔버·모터·UI 수정 없이 같은 결과를 재현했다. 후속 LW-07D의 현재 진행은 아래와 같다.
- **FANUC LW-07D 완료:** 목표 미리보기·최신 상태 재계산·6축 사전 검사·동기 관절 이동/정지 후 기본 정책의 고정 목표 100/100을 실제 TCP로 대조했다. 99개 이동/1개 허용 오차 안의 추가 이동 없음, 최대 0.0996463mm·0.0191007°다. 거부 4건 명령 보존·정지/축 비활성 중단과 현재값 복구·SCARA 실제 100개 도착/경로 회귀도 통과했다. 검증 도구의 float 누적 시간 차감 문제만 double 시간으로 고쳤으며 모터·솔버·제한은 유지했다. 새 이동 UI 안내 뒤 사용자가 다음 진행을 승인했다. 다음은 LW-08 경유점 설계부터 나눈다.
- **확대된 필수 범위:** SCARA와 FANUC 모두 자체 FK·IK로 최종 라인에서 운전한다. SCARA가 투입 상품을 인계대에 놓고 퇴피하면 FANUC가 받아 A/B로 분류한다. FANUC LW-07A~07D를 마쳤고 양쪽 경유점·단독 집기·LW-12A 순차 인계는 남아 있다.
- `RobotLab.unity`에는 모델 계층을 재사용하는 독립 `ScaraRobot_Work` 프리팹과 `MachineControlLab` 시험 프리팹이 있다. Starter Drive·Sensor·Grip·PLC 신호·자동 피킹·씬 컨트롤러를 제거했다. 자체 `RotaryAxis`가 0↔30° 이동·중간 정지를 처리하고 `PresenceSensor`가 실제 Trigger 접촉을 감지한다. Play 진입만으로 자동 운전하지 않는다.
- FANUC A1~A6·제공 TCP·집게 모델을 유지하고 제공 동작 13개와 Rigidbody·Collider를 제거한 뒤, 자체 `RotaryAxis` 6개와 `FanucJointLab`을 연결했다. 상단 `LineWatch → FANUC 조작 테스트` 전용 창에서 축별 이동·정지·복귀와 전체 정지·복귀·현재값 FK 진단이 가능하다. 시험 범위는 모두 ±45°·20°/초이며 실물 사양이 아니다. FANUC IK 목표 이동 연결·집기·충돌 회피는 남아 있다. SCARA·시험 설비의 위치와 기존 조작은 유지한다.
- 자체 구현은 **Editor Play 세 세션·총 9회**를 새로 검증했다. 이동·중간 정지·복귀·센서 진입·이탈과 추가 경계 시험을 통과했고 Play 콘솔 오류는 0건이었다. 마지막 세션은 Collider 제거 처리 보완 후 검증이다. 새 `Builds/Windows-OwnCode/LineWatch.exe`는 빌드 성공(오류 0·기존 HDRP 참조 경고 2) 상태지만 **새 exe 실행·종료 검증은 실행 권한 요청 거절로 미완료**다. 초기 LW-02 실행 이력과 구분한다.
- 전체 정적 검사는 기존 Volume·Starter 자산의 오류 20건·경고 9건으로 여전히 미통과다. 자체 코드·작업 프리팹·RobotLab 관련 오류는 0건이다. 새 보고서는 `Logs/LW03-OwnCode/project-meta-audit.json`이며 전체 프로젝트 오류 0으로 설명하지 않는다.
- 조작은 **상단 `LineWatch → 조작 테스트` 별도 창 또는 MachineControlLab Inspector 상단 버튼**에서 수행한다. 축 각도·이동 상태·센서 점유·진입·이탈 횟수를 표시한다. Play 전·일시정지 중에는 버튼을 비활성화하고 안내한다. 사용자가 새 패널의 정상 동작을 직접 확인했다. 코드 독립 리뷰는 미확인이다.
- 과정 ②는 Play를 종료한 편집 상태에서 작업했다. 격리된 프리팹을 변경·저장한 뒤 새로 불러 기준 좌표를 검증했다. 기존 RobotLab 씬은 dirty=false, 시험 설비의 Axis1 참조 유지, 콘솔 오류 0건이었다. 네 축 이동 시험은 하지 않았다. 다음 Editor 작업 전 상태를 다시 확인한다.
- 이후 FANUC 추가에서도 저장·씬 재열기와 Play 검사를 통과했다. 두 모델·기존 SCARA 연결 유지, 씬 누락 스크립트 0, 원본 Starter 스크립트·프리팹 의존성 0, 실제 Play 콘솔 오류 0이다. 모델 표시·참조 검사이며 FANUC 이동 검증이 아니다. 검증 후 Play를 종료했다.
- 후속 자체 구동 검증에서 FANUC ±15° 이동 12건·중간 정지 6건·전체 정지·복귀·잘못된 목표 거부를 통과했다. SCARA·센서 회귀 3회도 통과했다. 전용 창 최종 컴파일을 확인했고 사용자가 패널을 직접 시험해 정상 동작을 보고했다. 향후 실제 버튼 클릭 테스트는 사용자에게 요청하며 AI가 직접 수행하지 않는다. 사용자 독립 코드 리뷰는 미확인이다.
- SCARA ③은 ±20° 회전·중간 정지·홈 복귀, 50mm 하강·정지·복귀·150mm 끝점, 전체 정지·복귀와 잘못된 목표 거부를 통과했다. 기존 단일 축·센서 3회 회귀와 FANUC 참조 유지도 확인했다. 메뉴·명령 버튼 14개·목표 입력 4개의 구성을 스크립트로 읽었고 직접 클릭하지 않았다. 이후 사용자가 새 패널 수동 테스트의 정상 동작을 확인해 LW-04를 완료 처리했다. 독립 코드 리뷰는 미확인이며 실제 TCP 표시를 FK 솔버 완료로 취급하지 않는다. 사용자의 수동 시험 후 Editor 상태는 다음 조작 전에 확인한다.
- 이전 완료 커밋은 LW-03 `e44415e`, LW-04 `67a810c`, LW-05 `fba8a87`, LW-06 `c2aa778`이다. 2026-11-15 사용자 요청으로 SCARA LW-07 경로 개선·FANUC LW-07A~07D의 기하/FK/IK/이동과 검증 도구·문서를 이번 후속 커밋에 묶어 기록한다. 식별자는 `git log -1`로 확인한다. RobotLab 씬 구분 오브젝트·루트 순서와 `runInBackground`는 별도 사용자 변경으로 커밋에서 제외하고 작업 트리에 보존한다. 기존 Windows 실행물에는 LW-04 이후 변경이 포함되지 않으며 푸시는 하지 않는다. 이전 `codex.cs` 이동의 후속 처리 주체는 추정하지 않는다.

### 두 로봇을 모두 사용하는 완료 흐름 — 2026-11-14 계획 추가

- 역할은 우선 SCARA가 투입 상품을 집어 인계대에 놓고, FANUC가 받아 A/B로 분류하는 구조다. 인계대는 한 상품·한 로봇의 진입만 허용한다. SCARA 놓기→보유자 인계대 전환→SCARA 퇴피→FANUC 진입·집기→보유자 FANUC 전환→퇴피 순서를 확인한다.
- 인계대가 가득 찼거나 상대 로봇이 작업 중이면 정상 대기한다. 인계 중 일시정지·고장 시 상품 보유자와 점유 상태를 유지하고, 복구 조건을 확인한 뒤 명시적으로 재개한다. 직접 공중 전달·임의 장애물 회피는 구현 범위에 넣지 않는다.
- 의존 순서는 **LW-07 → 07A → 07B → 07C → 07D → 08~12 → 12A**다. 양쪽 FK·IK와 목표 이동을 확인하기 전 물류 통합 완료로 표시하지 않는다. 기존 SCARA 코드는 검증 기준으로 유지하고 FANUC는 별도 6축 솔버를 사용한다.
- FANUC는 위치 3축과 전체 회전 3축을 목표로 한다. 수치 해법과 현재 자세 기반 초기값을 우선 검토하되 구체 해법은 07C에서 검증한다. 미수렴·시간 예산 초과·제한·잘못된 입력을 구분하고 실패 시 새 명령을 보내지 않는다. 알고리즘 참고는 기획안의 Numerical IK 링크를 따른다.
- FANUC FK 100개 관절 자세, 작업용 IK 목표 100개, 각 로봇 단독 집기 10회, 연결 분류 상품 100개를 각각 다른 검증으로 기록한다. IK의 초기값·목표 집합·허용값·반복 예산을 실행 전에 고정하고 성공률·실패·계산 비용을 함께 남긴다. 최종 분류 100개는 상품마다 두 로봇의 실제 처리 기록과 배출을 확인한다.
- 로봇별 ID·기종·축 수·목표/실제 TCP·오차·실패 원인과 인계 상태를 운전·관제·서버·회귀 검증까지 유지한다. SCARA 수평각과 FANUC 전체 회전 오차를 혼용하지 않는다. 새 UI 직접 클릭은 사용자 담당이며 각 단계 완료 시 기여·검증·한계를 누적 기록한다.

#### ② 손목·TCP 배치와 좌표 기준 — 2026-11-13

작업 프리팹의 기존 메시를 유지하고 다음 Transform을 추가했다. `RobotFrame`은 루트의 직속 자식이며 Axis1 홈 피벗과 같은 위치라 관절과 함께 회전하지 않는다.

```text
ScaraRobot_Work
├─ RobotFrame                 # 로봇 기준 원점: 루트 로컬 (0, 0.228, 0)m
└─ Base/Axis1/Axis2/Axis3
                     └─ Axis4    # 로컬 위치·회전 0, 새 손목 피벗
                         └─ Gripper
                             └─ TCP
```

**좌표 규칙:** 1 Unity unit = 1m. 내부 직선값·치수는 m, 회전은 도(°), 화면에서 mm를 표시할 경우 ×1000으로 변환한다. RobotFrame은 +Y 위쪽, 모델 홈에서 팔이 뻗는 방향이 +X다. +Y축 +90° 회전은 +X를 -Z로 보낸다. 로봇 루트는 단위 스케일을 유지한다.

| 관절 | 종류·양의 방향 | 홈 명령값 | 과정 ③에서 적용할 시뮬레이션 범위 |
|---|---|---|---|
| q1 / Axis1 | 로컬 +Y 회전, 홈 회전에 상대적으로 적용 | 0° | -170°~+170°; 현재 단일 축 시험 설정을 유지 |
| q2 / Axis2 | 로컬 +Y 회전, Axis1에 상대적인 관절각 | 0° | -150°~+150° |
| q3 / Axis3 | 아래로 내려갈수록 양수. `homeLocalPosition - Vector3.up * q3` | 0m (위쪽 기준) | 0~0.15m (150mm 스트로크 초안) |
| q4 / Axis4 | 로컬 +Y 회전, Axis3에 상대적인 손목각 | 0° | -180°~+180° |

이 범위는 실물 사양·충돌 회피·안전 인증에서 얻은 값이 아니다. 소프트웨어 시험을 위한 설계 초안이며 전체 범위의 간섭·동작 검증은 아직 하지 않았다. q2=0인 홈은 완전 신장한 기하학적 영점이다. 실제 피킹 대기 자세와 특이 자세 처리는 후속 단계에서 별도로 정한다.

**TCP 규칙:** 가상 흡착 집게의 하단 중심을 이 프로젝트의 접촉 기준점으로 정한다. 원본 메시 bounds의 하단 중심을 사용한 설계 선택이며 실물 공구 교정값이 아니다. Gripper 로컬 위치는 `(0, -0.027277, 0)m`, 로컬 Y 회전은 -90°다. Axis3의 모델 홈 회전 +90°와 상쇄되어 모든 명령값이 0일 때 TCP의 방향이 RobotFrame과 같아진다. 접근 방향은 TCP의 -Y다. 모델 메시와 Gripper의 기존 홈 회전은 변경하지 않았다.

- 홈 TCP 좌표: RobotFrame 기준 약 `(0.700000, -0.115177, 0)m`, 수평 회전 0°. 도구 오프셋은 Axis3 기준 Y 약 -0.034177m이며 링크 높이 오프셋과 분리한다.

#### ① FK 계산 기준·공식·기준 자세 — 2026-11-13

**입력·좌표:** q1·q2·q4는 각 RotaryAxis의 `CurrentPosition`(도), d3는 LinearAxis의 `CurrentPosition`(m)다. 목표값을 사용하면 이동 중 현재 모델과 계산 결과가 달라지므로 목표와 현재를 구분한다. 결과 위치는 RobotFrame 기준 m, 방향은 해당 기준의 수평 회전각이다. 삼각함수 입력만 라디안으로 변환한다. 정적 치수는 홈 기하 정보에서 정하고 운전 중 실제 TCP 위치를 FK 입력으로 다시 사용하지 않는다.

| 기하 입력 | 현재 값 | 의미 |
|---|---|---|
| L1, L2 | 0.325m, 0.375m | 수평 링크 길이. 관절 사이 3D 거리와 구분 |
| h12, h23 | +0.016783m, -0.097783m | 두 링크의 홈 높이 차. 합은 -0.081m |
| t = (tx, ty, tz) | (0, -0.034177, 0)m | 모든 관절이 0일 때 Axis4 피벗→TCP 벡터를 RobotFrame 축 방향으로 표현. Gripper -0.0069m와 TCP -0.027277m를 포함 |
| psi0 | 0° | 모든 관절 0일 때 TCP의 RobotFrame 기준 홈 수평각. 모델 +90°와 TCP 보정 -90°가 상쇄 |

관절의 양의 +Y 회전이 +X를 -Z로 보내므로 Z 식의 사인 항에는 음수가 붙는다. 아래 a·b·c는 라디안이고 q값은 도다.

```text
a = q1 * pi / 180
b = q2 * pi / 180
c = (q1 + q2 + q4) * pi / 180

x = L1*cos(a) + L2*cos(a+b) + tx*cos(c) + tz*sin(c)
y = h12 + h23 - d3 + ty
z = -L1*sin(a) - L2*sin(a+b) - tx*sin(c) + tz*cos(c)
yawDegrees = normalizeDegrees(q1 + q2 + q4 + psi0)
```

이는 손목 피벗 위치에 도구 벡터를 회전해 더하는 식이다. 현재 도구는 중심선에 있어 tx=tz=0이므로 손목 q4는 위치를 바꾸지 않고 방향을 바꾼다. 나중에 수평 도구 오프셋이 생기면 q4도 TCP 위치에 영향을 준다. psi0는 도구 방향의 영점이며 도구 위치 회전 c에 추가로 더하지 않는다. 현재 모델의 90°를 yaw에 다시 더해 이중 보정하지 않는다.

월드 좌표는 로봇 기준 결과를 RobotFrame의 위치·회전으로 변환한다. 단위 스케일 기준 `pWorld = frame.position + frame.rotation * pRobot`, `qWorld = frame.rotation * yawRotation`이다. 월드 Euler 각을 단순히 더하지 않는다. 위치 오차는 두 위치의 거리(m), 표시 mm는 ×1000이다. 수평각 오차는 360° 경계를 고려한 최단 차이를 사용한다. 예를 들어 +179°와 -179°의 차이는 2°다.

**손계산 기준표:** 위치는 mm, d3는 m다. 반올림한 0은 원래의 부동소수점 미세 오차를 생략한 표현이다.

| q1 | q2 | d3 | q4 | 예상 TCP (X, Y, Z) mm | 수평각 |
|---|---|---|---|---|---|
| 0° | 0° | 0 | 0° | (700, -115.177, 0) | 0° |
| +90° | 0° | 0 | 0° | (0, -115.177, -700) | +90° |
| -90° | 0° | 0 | 0° | (0, -115.177, +700) | -90° |
| 0° | +90° | 0 | 0° | (325, -115.177, -375) | +90° |
| +90° | -90° | 0 | 0° | (375, -115.177, -325) | 0° |
| 0° | 0° | 0.050 | 0° | (700, -165.177, 0) | 0° |
| 0° | 0° | 0 | +90° | (700, -115.177, 0) | +90° |
| +45° | 0° | 0.050 | -45° | (494.974747, -165.177, -494.974747) | 0° |

- 검증 방식: 저장 프리팹을 격리해 불러 위의 고정 관절 자세만 임시 적용하고 TCP를 읽어 손계산 값과 비교했다. 모터 명령·Play·실제 버튼 클릭을 실행하지 않았고 복사본도 저장하지 않았다. 최대 위치 차이 1.38388387e-7m(약 0.000138mm), 수평각 차이 0.0000305176°로 8개 모두 통과했다. 작업 전후 원본 프리팹 SHA-256이 동일했다.

#### ② 자체 FK 함수 구현·검증 — 2026-11-14

- 코드: `Assets/02.Scripts/LineWatch/ScaraForwardKinematics.cs`. MonoBehaviour가 아닌 순수 계산 클래스다. `Geometry`는 링크 길이·높이 차·홈의 도구 벡터·도구 수평각을, `TcpPose`는 결과 위치·수평각을 담는 읽기 전용 값 형식이다. 함수는 Transform·씬·에셋 구동을 읽거나 움직이지 않는다.
- API: `ScaraForwardKinematics.Calculate(q1Degrees, q2Degrees, d3Metres, q4Degrees, geometry)`. 출력 `PositionMetres`는 RobotFrame 기준 m, `YawDegrees`는 -180~180°로 정리한 수평각이다. +180°와 -180°는 같은 방향이다. 호출부에서 현재 관절값을 전달하는 연결은 과정 ③에서 한다.
- 치수는 하드코딩된 숨은 기본값 대신 Geometry 입력으로 받는다. 현재 모델의 사용 예는 다음과 같다.

```csharp
var geometry = new ScaraForwardKinematics.Geometry(
    0.325f, 0.375f, 0.016783f, -0.097783f,
    new Vector3(0f, -0.034177f, 0f));
var pose = ScaraForwardKinematics.Calculate(0f, 0f, 0.05f, 0f, geometry);
// PositionMetres ≈ (0.700, -0.165177, 0), YawDegrees = 0
```

#### ① 입력·공식·고정 기준 해 — 2026-11-14

이번 범위는 계산 기준과 고정 기준 해 확인이다. 런타임 IK 함수·조작 UI·모터 코드는 아직 변경하지 않는다. 현재 도구처럼 수평 편심이 없는 경우만 전제하지 않도록 기존 FK의 도구 벡터와 홈 수평각을 그대로 사용한다.

| 항목 | 기준 |
|---|---|
| 목표 | RobotFrame 기준 TCP `(x,y,z)` m·수평각 `psi` °. 롤·피치 입력은 없다. UI는 mm를 m로 변환한다. 월드 목표의 좌표 변환은 호출부의 역할이다. |
| 기하 입력 | 기존 FK Geometry: L1·L2·h12·h23·홈 도구 벡터 `(tx,ty,tz)`·홈 수평각 `psi0`. 실측 TCP에서 자동 보정하지 않는다. |
| 출력 후보 | 홈 기준 `(q1°,q2°,d3 m,q4°)`. d3는 아래로 양수이며 계산 자체는 움직임을 명령하지 않는다. |
| 관절 제한 | 현재 q1 ±170°·q2 ±150°·d3 0~0.15m·q4 ±180°. 기하적으로 닿는 것과 제한 안에서 실행 가능한 것을 구분한다. |

아래 삼각함수 계산은 라디안이며 입출력 회전 단위는 도다. `c`는 관절 회전 합이므로 도구 방향 영점 `psi0`를 목표에서 먼저 뺀다. 홈 도구 위치 벡터에 `psi0`를 다시 더해 회전시키지 않는다.

```text
c = psi - psi0
wx = x - (tx*cos(c) + tz*sin(c))
wz = z - (-tx*sin(c) + tz*cos(c))
u = wx, v = -wz
D = (u*u + v*v - L1*L1 - L2*L2) / (2*L1*L2)
q2 = atan2(+sqrt(1-D*D), D) 또는 atan2(-sqrt(1-D*D), D)
q1 = atan2(v,u) - atan2(L2*sin(q2), L1 + L2*cos(q2))
d3 = h12 + h23 + ty - y
q4 = c - q1 - q2  (360° 주기의 동치 후보 포함)
```

- Unity +Y 회전에서 +X가 -Z로 향하므로 평면 역산은 `(wx,-wz)`를 사용한다. 먼저 목표 방향으로 회전한 도구 편심을 TCP에서 빼야 링크 끝의 목표가 된다.
- 링크만의 기하 범위는 `abs(L1-L2) <= sqrt(u²+v²) <= L1+L2`, 현재 50~700mm다. 이는 실제 허용 작업영역 전체가 아니다. q2 제한 때문에 완전히 접힌 안쪽 경계는 제외되며 q1·q4·d3 제한도 별도로 적용한다.
- NaN/Infinity·유효하지 않은 치수는 잘못된 입력으로, 링크 범위 밖은 도달 불가로, 기하 해는 있지만 제한 안 후보가 없으면 관절 제한으로 구분한다. d3 범위도 관절 제한이다. 실패 시 임의 관절값이나 이동 명령을 반환하지 않는다.
- 계획한 수치 정책: D가 ±1을 넘은 경우 차이가 1e-6 이하인 반올림 범위에서만 ±1로 보정하고, 그 밖은 도달 불가로 처리한다. 관절 제한을 맞추기 위해 목표를 잘라내지 않는다. 후보는 FK에 다시 넣어 목표 오차도 확인한다. 이 정책의 경계 검증은 과정 ②에서 수행한다.
- 각도 하나를 무조건 -180~180°로 정리한 뒤 끝내지 않는다. 각 관절 제한 안의 `angle+360*k` 동치값을 확인한다. q4의 +180/-180처럼 같은 방향인 후보도 실제 축 이동량은 다를 수 있다.

- 선택은 순수 계산과 분리한다. 먼저 유효 후보들을 보여주고, 자동 선택이 필요하면 현재 관절값과의 `dq1²+dq2²+dq4²`가 작은 후보를 사용한다. d3는 같은 목표에서 공통이라 후보 비교에서 제외한다. 제한된 축의 실제 이동이므로 각도 차이를 무조건 최단 회전으로 감싸지 않는다. 동률이면 q2 양수 해를 먼저 둔다. 수동 해 선택도 같은 제한 검사를 따른다.

**문제와 설계 변경**

목표점 근처의 큰 관절 변화가 항상 잘못된 것은 아니다. 기존 필터는 관절을 재배치하는 이동과 TCP 직선을 유지하는 작업을 목표 거리·각도로 추측했다. 이를 `MotionMode.Joint/Linear`로 명시하고 기존 공간/각도 임계값·수락 목표 캐시를 제거했다. 이동 개념은 [UR MoveJ/MoveL 문서](https://www.universal-robots.com/manuals/EN/HTML/SW5_19/Content/prod-usr-man/complianceUR30/SW_sections/first_program/move.htm), 경로·시간 분리는 [Modern Robotics 9.1/9.2](https://modernrobotics.northwestern.edu/nu-gm-book-resource/9-1-and-9-2-point-to-point-trajectories-part-2-of-2/)를 참고했다. 이 구현을 해당 제어기의 전체 기능 복제로 표현하지 않는다.

**현재 구현**

- `ScaraMotionPlanner`는 순수 계산 클래스다. 입력은 실제 현재 관절값·목표 위치/수평각·기하·관절 제한·기존 축 속도이며, 수정할 수 없는 구간 목록·최종 해·소요 시간을 반환한다. 프리팹이나 Transform을 읽거나 움직이지 않는다.
- 관절 모드는 유효한 끝점 해를 선택해 시작/끝 관절 공간을 선형 보간한다. 각 관절 제한은 구간 안에서도 유지되며, 큰 총 회전량을 거절하지 않는다. `max(abs(dq_i)/v_i)`로 각 구간 시간을 정하고 공통 진행률로 동기 도착한다. 기본 API는 이 모드로 유지해 기존 목표 이동 계약을 보존한다.
- 직선 모드는 TCP 위치와 수평각의 최단 방향을 보간한다. 시작 q2 분기를 유지하고 q1/q2 각도는 이전 값에서 연속적으로 풀어낸다. q4는 보간한 누적 수평각에서 q1/q2·도구 영점 방향을 빼 계산한다. 그러므로 ±180° 표시 전환으로 실제 회전 제한을 건너뛰지 않는다. 완전 신장 시작에서는 양쪽 분기를 검토하며 명시 선택이 현재 분기와 다르면 관절 이동을 안내한다.
- 실제 실행은 관절 구간 보간이다. TCP의 곡선이 목표 직선에서 벗어나는 상한을 `(|L1|*dq1² + |L2|*(dq1+dq2)² + rho*(dq1+dq2+dq4)²)/8 + 수치 여유`로 계산한다. 각도는 rad, rho는 수평 도구 편심 길이다. 이는 구간 내 FK 위치의 2차 미분 상한으로부터 얻는 선형 보간 오차 한계다. 0.1mm 이내가 될 때까지 구간을 세분하며 총 관절 변화 15° 같은 거절 조건은 사용하지 않는다.
- 분할은 최대 4,096개 노드·깊이 20의 계산 예산을 둔다. 기하/설정 오류·중간 도달 불가·현재 분기/회전 한계·분할 한도 미검증을 구분한다. 끝점 해가 있어도 직선 경로가 성립하지 않을 수 있고, 실패 때 관절 모드로 조용히 바꾸지 않는다. 기하 입력과 실제 TCP가 맞지 않는 경우도 직선 계획을 거부한다.
- `ScaraJointLab.FixedUpdate`는 검증한 동일 구간과 시간 배분을 실행한다. 두 축 클래스는 경로 제어 중 자체 MoveTowards 갱신을 건너뛰고, 제어기가 네 축을 함께 적용한다. 최종 TargetPosition은 유지하며 CurrentPosition·FK 진단은 실제 중간값을 읽는다. 새 요청은 현재 실제 자세에서 재계획하고 전부 검증한 후 기존 계획을 교체한다. 실패는 기존 계획·목표·현재값·이동 플래그를 유지한다.
- 전체/개별 정지, 수락한 수동 조작은 경로를 취소한다. 실행 중 축 비활성화·속도 설정 변경·허용 범위 위반이 감지되면 전체 경로를 멈추고 원인을 남긴다. 독립 수동 축·홈·FANUC의 기존 단독 구동은 유지한다. IK 목표 이동만 동기 계획을 사용하며 수동 홈 조작까지 동기 이동으로 재구현한 것은 아니다.
- UI에는 `관절 이동 (동기 도착)`·`직선 작업 이동`을 추가하고 기존 해 선택·후보·경고·정지를 유지했다. 기본은 관절 모드다. 직선 실패는 선택 없음·버튼 잠금·경유점/관절 이동 안내로 표시한다. 실행 중·수동 축 이동·정지·실행 중단 원인도 구분한다. 가속도·충돌 미검증을 UI에 명시했다.

**과정 ① 계약·검증 기록**

- 입력: RobotFrame 기준 목표 위치(m), 목표 단위 Quaternion `(x,y,z,w)`, 초기 관절값 6개(°), 저장 기하와 관절 제한을 받는다. 외부 단위는 기존 FK와 맞추고 내부 보정량은 rad로 계산한다. 초기값이 제한 밖이거나 유한하지 않으면 잘못된 입력으로 처리하며 임의로 잘라내지 않는다. 0/NaN/Infinity Quaternion을 identity로 대체하지 않는다.
- 오차: 위치 `dp = 목표 위치 − FK 위치`, 전체 방향 `dr = LogSO3(목표 Quaternion × inverse(FK Quaternion))`를 모두 RobotFrame에서 표현한다. 상대 Quaternion의 w가 음수이면 전체 부호를 반전해 짧은 회전을 사용한다. q/−q는 같은 회전이며 π 회전의 축 부호는 비유일하다. 이 계약은 분리된 위치/회전 벡터 오차와 기하 Jacobian이며 교재의 body twist/SE(3) log를 그대로 혼합한 식이 아니다.
- Jacobian: 각 관절의 RobotFrame 피벗 `o_i`·단위 축 `a_i`를 현재 관절값에서 합성하고 열을 `[a_i × (TCP−o_i); a_i]`로 만든다. 단위는 선형 m/rad·각속도 rad/rad다. 큰 회전의 Log 오차에 대한 정확한 미분 전체와 기하 속도 Jacobian을 혼동하지 않는다. 다음 구현에서는 이를 국소 보정 모델로 사용하고 실제 목표 오차가 줄어드는지 별도로 확인한다.
- 수치 방식의 초기 선택: `e=[dp/L; dr]`, `J_n=[J_p/L; J_r]`, `L=0.5m`로 위치와 방향의 수치 척도를 맞추고 `(J_nᵀJ_n + λ²I)Δq = J_nᵀe` 감쇠 최소제곱 보정을 우선 구현한다. λ 조절과 실제 오차 감소 확인·관절 경계 처리를 실험한다. L은 프로젝트의 초기 비용 척도이지 도달 범위나 이동 거절 기준이 아니다. 성공 판정은 가중 합만 보지 않고 물리 단위의 위치·각도 오차를 각각 검사한다. 이 방법이 모든 초기값에서 수렴을 보장한다고 주장하지 않는다.
- 성공 기준: 위치 0.0001m(0.1mm) 이하·전체 회전 0.05° 이하·모든 관절 제한을 동시에 만족한 경우만 성공 해를 반환한다. 후속 LW-07D의 2mm·0.5° 기준에 계산 오차 예산을 남기기 위한 초기 목표이며 실제 합격 결과로 쓰지 않는다. 반복·총 시간 예산은 ②에서 실측 후 수치로 고정하고 여러 초기값을 시도해도 총 예산을 넘기지 않는다.
- 결과/실패: 성공 시에만 명령 가능한 관절 해를 제공하고 위치/회전 잔차·반복 수·시간·사용 초기값을 함께 기록한다. 잘못된 입력/기하/초기값, 외곽 반경 밖, 반복 예산 초과, 시간 예산 초과, 정체/관절 경계 정체, 수치 실패를 구분한다. 미수렴·관절 경계 정체는 이번 탐색에서 해를 찾지 못했다는 뜻이며 전역적 도달 불가의 증명이 아니다. 실패는 모터 상태를 바꾸지 않는다(이동 연결 자체는 LW-07D).
- 기준 목표: 홈, 홈 근처, 일반 양/음 자세, 제한 근처, 손목 복합의 6개를 ±45° 안의 알려진 관절값으로 만들고 격리 모델에 대조했다. 목표별 위치·Quaternion·검증용 관절값은 `Logs/LW07C/reference-goals.json`에 있다. 예를 들어 일반 양 자세의 목표는 약 `(0.086897,0.986332,-0.938834)m`, Quaternion `(-0.636373,-0.738031,-0.209741,0.079685)`다. 이 목표의 알려진 관절값 `(15,-20,25,-15,20,10)°`는 검증에만 쓰고 풀이 초기값으로 주지 않는다.
- 초기값: 홈 `(0,0,0,0,0,0)°`, 고정 대체 1 `(10,-15,25,15,20,-10)°`, 대체 2 `(-10,15,-25,-15,-20,10)°`를 별도로 고정했다. 홈→홈은 이미 해인 경우의 대조군으로만 보고 별도 성공률 설명에서 구분한다. 홈은 rank 5, 두 대체 초기값은 rank 6이었다. 미확인 시드를 정답 관절값으로 바꿔 성공을 꾸미지 않는다.
- 실제 발견: 홈의 수치적 Jacobian rank가 5였다(위치 척도 0.5m, 부분 피벗 소거 상대 허용치 1e-6). 나머지 기준 목표 5개는 6이었다. 따라서 홈을 일반적인 비특이 초기값으로 가정하거나 행렬의 단순 역을 강제하지 않는다. 다만 홈 자체는 정확히 도달 가능하므로 rank 부족을 즉시 실패 조건으로 쓰지 않는다. rank 추정은 이번 조사이며 전체 특이점 집합·조건수나 IK 성공률을 측정한 것은 아니다.
- 기초 검증: 6개 자세×6개 Jacobian 열을 ±0.001rad FK 중앙 차분과 비교했다. 선형 최대 차이 `9.64510255e-5m/rad`, 각속도 최대 차이 `9.22083855e-5`로 각 0.001 기준 이내였다. 회전 벡터는 q/−q·작은 각·±180° 경계·반회전·비가환 좌표계 사례 5개를 통과했다. 준비 목표의 FK/격리 모델 최대 차이는 `2.92001943e-7m`·`1.13122824e-5°`다. 이는 IK 해 탐색 검증이 아니며 IK 풀이 횟수는 0이다.
- 확실한 도달 불가: 단위 회전이 링크 이동 벡터 길이를 보존한다는 삼각 부등식으로 `||p|| ≤ Σ||홈 이동 벡터|| + ||도구 벡터|| ≈ 1.73527754m` 외곽 상한을 얻었다. `(3,0,0)m`은 그 밖이며 수치 여유 0.00001m를 두어도 분명하다. 이 구 안쪽은 관절 제한·자세 제약 때문에 도달 불가능할 수도 있다. 외곽 상한은 정확한 작업공간 경계가 아니다.

이 기준은 LineWatch 작업에만 적용한다.

**2026-11-14 사용자 지침:** 의미 있는 문제의 발견·원인 확인·수정·검증이 진행될 때마다 README의 관련 사례를 중간 갱신한다. LW 완료 시점까지 기록을 미루지 않는다. `문제 현상·재현 조건 → 원인 → 수정 방법과 선택 이유 → 검증 결과(가능하면 전후 수치·근거 경로) → 남은 한계`를 짧게 연결한다. 조사 중이면 확인된 사실·미확인 원인·다음 확인을 구분하고, 예상 결과를 실제 검증 결과로 적지 않는다.

**포트폴리오·면접 설명 기준 추가:** 설정값만으로 해결을 설명하지 않는다. 원인·이동 의도·책임 분리·실패 처리·검증 설계와 결과를 연결한다. 초기 임계값 필터는 한계가 있는 이전 시도로 보존하고 현재는 관절/직선 구분·중간 경로·속도 동기화의 실제 구현과 비교 결과로 설명한다. 가속도·충돌·일반 작업 전체의 거절률 등 미검증 범위는 성과로 포장하지 않는다.

- 각 LW를 마칠 때 포트폴리오에 설명할 가치가 있는 설계 판단, 문제 해결, 재현 가능한 검증이나 측정 결과가 있으면 README의 관련 사례를 추가·갱신한다.
- 제약 또는 문제, 선택한 방법과 이유, 검증 근거와 실제 결과, 남은 한계를 짧게 연결해 작성한다. 기존 설명과 겹치면 새 절을 늘리기보다 해당 내용을 갱신한다.
- 사용자 직접 작업, AI 작성·검증 작업, Starter 제공 기능을 구분하고 구현 예정과 완료 상태를 명시한다. 확인하지 않은 개인 기여·검토 완료·성과 수치는 작성하지 않는다.
- 단순 파일 이동·기본 배치·반복 설치 등 설명 가치가 작으면 포트폴리오 사례를 억지로 추가하지 않는다. 작업 상태와 완료 근거는 이 체크리스트에 남긴다.

### 대화가 바뀌어도 유지할 기록

- 각 LW 완료 또는 대화 종료 시점에 위 '새 대화 인수인계'의 현재 단계·다음 작업·미해결 사항·Git 상태를 갱신한다. 같은 내용을 별도 인수인계 파일로 늘리지 않는다.
- '기여와 검증 누적 이력'에 날짜·작업 ID·사용자 직접 작업 또는 결정·AI 작성/실행 작업·증거·미확인 항목을 추가한다. 기존 기록을 후속 작업으로 덮어쓰지 않는다. 이전 기록에 오류가 있으면 정정 이유를 남긴다.
- 사용자 수동 검증, AI 자동 검증, 제공 에셋 기능을 구분한다. 사용자의 지시·승인은 사용자 결정으로 기록하고, AI가 작성·실행한 코드를 사용자가 직접 작성·검증한 것으로 바꾸지 않는다.
- 실제 생성·확인한 보고서 경로와 측정값, 실행 환경(Editor/빌드), 커밋 해시를 남긴다. 파일이 없는 경우 이전 기록과 새 재현 결과를 구분하고, 확인하지 않은 수치를 채우지 않는다.
- 최종 대화에서는 누적 이력·README 역할 분담·단계별 완료 기록을 대조해 포트폴리오를 정리한다. 현재 완료 기능과 예정 기능, 사용자가 직접 설명·재현한 범위와 아직 미확인인 범위를 함께 확인한다.

## 범위를 지키는 기준

- 첫 완성판에서 SCARA와 FANUC 모두 자체 FK·IK와 집기 역할을 수행한다. 현재 FANUC는 수동 조작·FK/진단·순수 IK와 전체 검증을 마쳤고 목표 이동·집기·통합은 남아 있다. 완료 여부·제한·검증 근거는 기종별로 구분한다. 여러 셀 부하는 성능 검증 단계에서 늘린다.
- 4축 SCARA 경계를 확인한 뒤 6축 FANUC 위치·자세 제어와 각 로봇의 고정 경유점을 완성한다. 물건은 고정 인계대에서 순차 전달한다. 임의 장애물 회피 경로 계획은 후속 과제로 둔다.
- 실물 PLC 없이도 외부 서버와의 실제 통신을 구현한다. 가상 데이터 사용 여부를 명시한다.
- 상세 화면 꾸미기와 차트는 정확한 상태·수량·알람 연결 후 진행한다.
- 대기열로 발생한 정상 대기는 적체 고장과 구분한다.
- 상품 수량, 축 단위, 도구 오프셋, 상태 전이가 맞지 않으면 다음 큰 기능으로 넘어가지 않는다.
- 업체 패키지·샘플·유료 에셋 원본은 공개하지 않는다. 자체 코드·설정·문서의 공개 범위를 확인한다.
