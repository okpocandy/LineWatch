# LineWatch 포트폴리오 기획안

## 1. 작품과 목표

**LineWatch — 로봇 피킹·분류 라인 관제 시뮬레이터**

- 프로젝트 폴더: `D:\Unity_study\LineWatch`
- Unity 제품명·기본 C# 네임스페이스: `LineWatch`
- 기본 앱 식별자: `com.portfolio.linewatch`
- 기획 문서: `Assets/Docs/Starter_Portfolio_Plan.md`

컨베이어가 상자를 피킹 위치로 운반하면, 직접 구현한 역기구학(IK)으로 로봇을 움직여 목적지 A/B에 분류한다. 사용자는 설비를 선택해 상태를 확인하고, 적체나 고장이 발생하면 알람의 위치와 원인을 확인한 뒤 복구한다. 별도 서버와 상태·명령을 교환하며 통신 장애에도 화면과 로컬 조작이 동작하도록 만든다.

목표 직무는 Unity 기반 디지털트윈·산업 시뮬레이션·3D 시각화 개발자다. C# 제어 로직, 좌표 변환과 로봇 기구학, 3D와 UI의 통합, 외부 시스템 연동, 오류 대응 및 측정 능력을 보여준다.

실제 설비 연결 전까지 작품을 **가상 설비 데이터를 사용하는 관제 시뮬레이터**로 소개한다. 실제 PLC 연동, 현장 검증 또는 안전 인증을 구현했다고 표현하지 않는다.

## 2. 개발 전제와 범위

- 1인 개발, Windows PC 실행 버전을 우선 완성한다.
- Unity 6000.3.21f1 / URP와 realvirtual Starter 6.3.6을 사용한다. 설치, Both 입력 설정, Getting Started 데모의 실제 동작을 확인했다.
- 개발 프로젝트는 D:\Unity_study\LineWatch로 확정했다. 기존 LineWatch 프로젝트에서 자체 작업 씬과 프리팹을 만든다. 작품의 공간은 물류 셀과 작업장으로 한정한다.
- 실행 순서와 완료 기준은 [작업 체크리스트](LineWatch_Work_Plan.md)를 따른다. 초기 씬·Windows 실행·Starter 연결 검증 후, 2026-11-13 요청으로 모델과 동작 코드를 분리했다. 현재 단일 축·센서는 자체 코드의 Editor Play 검증을 완료했고 새 Windows 빌드도 성공했다. 새 exe 실행·종료는 미검증이며 초기 LW-02 실행 이력과 구분한다. 역할 분담은 README에 기록한다.
- 실제 PLC·실물 로봇, 유료 Pro 기능, 별도 웹 대시보드, XR, 멀티플레이는 첫 버전에서 제외한다. 가상 로봇과 자체 IK 구현은 작품의 핵심 범위에 포함한다.
- 제공 데모는 학습용으로 사용한다. 제출용 라인은 모델·시각 자산을 직접 배치하고 설비 동작과 진행은 자체 C#으로 구현한다. UI 등 제작이 어려운 표현 요소는 에셋을 활용할 수 있다.

## 3. 첫 완성판의 물류 셀

```text
상품 생성 → 투입 컨베이어 → 감지·정지 위치 → 로봇 피킹 → A 출구
                                                      └→ B 출구

Unity 설비 상태 → 별도 C# 서버 → 상태·이벤트 보관
Unity 명령 조회 ← 별도 C# 서버 ← 외부 조작 요청
```

- 상품은 ID와 목적지 A/B를 가진다. 분류 정보는 가상 상품 데이터이며, 센서는 물체의 존재와 통과를 감지한다. 카메라 기반 바코드 인식은 구현 범위가 아니다.
- 컨베이어·센서·구동부·그리퍼의 외형은 에셋을 활용할 수 있다. 이송·감지·관절 이동·집기·놓기·피킹 순서는 자체 코드로 구현한다. 센서는 Unity Collider·Rigidbody의 물리 접촉을 사용한다.
- 라인은 한 번에 하나의 상자를 피킹 위치에 정렬하고 정지시킨다. 초기 버전은 이동 중인 상자를 추적해 집는 기능을 넣지 않는다.
- 로봇의 정상 작업 대기와 고장성 적체를 구분한다. 정상적인 피킹 대기를 알람으로 처리하지 않으며, 대기열이 가득 차면 상품 투입을 멈춘다.
- 생산 완료는 A/B 출구에 실제 도착한 상품으로 집계한다. 정지·재개나 중복 센서 이벤트로 같은 상품을 두 번 집계하지 않는다.
- 한 번의 테스트 실행에서 생성량, 완료량, 라인 잔류량과 제거량의 관계를 확인할 수 있게 한다.

### 설비 상태와 조작

| 상태 | 의미 | 허용 조작 |
|---|---|---|
| Stopped | 초기 상태 또는 정지 후 대기 | 시작, 시나리오 초기화 |
| Running | 상품 투입과 분류 진행 | 일시정지, 정지 |
| Paused | 현재 상품을 유지하며 일시정지 | 재개, 정지 |
| Faulted | 적체 또는 설비 고장으로 정지 | 원인 제거, 고장 해제, 정지 |

고장 원인을 제거하고 해제해도 자동으로 재가동하지 않는다. 사용자가 시작을 요청하면 운전한다. 정지와 초기화는 구분하며, 초기화가 상품과 통계에 미치는 영향도 화면에 표시한다.

### 필수 시나리오 네 가지

1. **정상 분류:** A/B 상품이 지정된 출구로 이동하고 실적에 한 번씩 반영된다.
2. **라인 적체:** 지정 구간의 장애물로 센서 점유가 임계 시간 이상 지속되면 알람과 정지가 발생한다. 장애물 제거와 고장 해제 후 다시 시작할 수 있다.
3. **서버 연결 끊김:** 오프라인과 마지막 정상 통신 시간을 표시한다. 로컬 시뮬레이션은 계속 동작하고, 재연결하면 최신 상태를 전송한다.
4. **로봇 목표 오류:** 도달할 수 없거나 관절 제한을 위반하는 목표를 지정하면 실행을 거부하고 원인을 표시한다. 상품을 순간 이동시키거나 실패한 동작을 완료로 집계하지 않는다.

적체 판정 시간과 생성 간격은 시나리오 설정으로 관리한다. 같은 초기 상태와 입력 순서로 다시 실행할 수 있어야 한다. 물리 결과의 완전한 결정성을 보장한다고 주장하지 않는다.

## 5. 에셋 활용과 직접 구현의 경계

| 에셋 활용 가능 범위 | 프로젝트 자체 코드 및 검증 |
|---|---|
| 컨베이어·센서·로봇·그리퍼·상품의 모델·재질·텍스처 | 축 구동, 감지, 이송, 생성·소멸, 집기·놓기, 분류 규칙, 운전 상태 전이 |
| 관절이 분리된 모델 계층·피벗 | FK·IK 계산, 관절 제한과 해 선택, 이동 및 피킹 순서 |
| UI 레이아웃·아이콘·폰트 등 제작이 어려운 표현 요소 | 설비 상태 연결, 검색·선택 동작, 알람과 실적 집계, 외부 서버 어댑터 |
| 제공 샘플과 문서의 학습용 참고 | 정상·고장·통신 장애 시나리오, 부하 정의, 검증과 성능 분석 |

패키지 원본은 수정하지 않는다. 작업 프리팹은 시각 모델을 유지하고 Starter Drive·Sensor·Grip·PLC 신호·자동 피킹 및 시뮬레이션 컨트롤러를 제거한다. 현재 RobotLab의 에셋 스크립트·프리팹 의존성은 0개이며 모델·재질 참조는 유지한다. Unity 엔진의 Transform·PhysX·렌더링·UI API는 사용한다. 에셋 UI 등 표현 기능을 활용하면 범위를 README와 영상에 명시한다. 구현과 자동 검증의 AI 지원 여부도 별도로 기록한다.

### 직접 구현하는 역기구학

**모델 제공 여부와 IK 제공 여부를 구분한다.** 공식 기능표에서 Robot Inverse Kinematics는 Professional 전용이다. 2026-11-11 설치 점검에서 Starter 6.3.6의 `Assets/3DPrefabs/ScaraRobot.prefab`과 FBX 모델을 확인했다. 프리팹에는 `Axis1/Axis2/Axis3`의 Drive 3개, Grip, Sensor, `LogicMove3AxisPickAndPlace`가 포함돼 있다. 이것만으로 자체 IK나 4축 제어가 구현됐다고 판단하지 않는다. 관절 분리·피벗·축 구성을 확인해 모델 외형을 활용하고, 필요한 손목 축은 추가한다. 구조가 맞지 않으면 Unity 기본 도형으로 4축 SCARA를 만든다. Pro 코드나 유료 솔버에 의존하지 않고 자체 솔버를 구현한다.

초기 대상은 **4축 SCARA(R-R-P-R)**다. 평면의 두 회전 관절, 수직 이동축, 손목 회전축을 제어한다. 작업 목표는 TCP(집게 끝)의 3차원 위치와 수평 회전각이며, 임의의 기울기까지 맞추는 6자유도 자세 제어는 아니다.

- **계산:** 두 링크 평면 로봇의 해석적 IK로 두 회전 관절을 계산하고, 높이와 손목 회전을 결합한다. FK도 별도로 구현해 계산 결과와 실제 Transform 계층의 TCP를 비교한다.
- **해 선택:** elbow-up/down 후보 중 관절 제한을 만족하고 현재 자세에서 변화가 작은 해를 선택한다. 목표가 조금 움직였을 때 관절이 갑자기 반대쪽으로 뒤집히지 않게 한다.
- **경계 처리:** 작업 범위, 수직축 한계, 관절 제한, 완전히 펴지는 자세 근처를 처리한다. 실패·특이 자세 근접 상태를 UI에 표시하며 실패를 성공으로 숨기지 않는다.
- **좌표와 구동:** 솔버는 로봇 기준 좌표와 일관된 단위를 사용한다. 월드 좌표, 모델 피벗, 도구 오프셋과 자체 축 단위의 변환을 연결부에 모은다. IK와 애니메이션·물리 등이 같은 관절을 동시에 제어하지 않게 한다.
- **동작:** 접근 → 하강 → 집기 → 상승 → 목적지 이동 → 하강 → 놓기 → 복귀 순서로 제어한다. 관절별 속도를 제한하고 정해진 안전 경유점을 사용한다.
- **범위:** 정해진 셀에서의 피킹을 완성한다. 임의 장애물에 대한 자동 경로 계획이나 실제 로봇 제어·안전 검증까지 구현했다고 주장하지 않는다.

검증 기준은 다음과 같다.

1. 미리 계산 가능한 기준 자세와 관절별 단독 움직임으로 축·부호·링크 길이를 확인한다.
2. 유효한 관절 값에서 만든 도달 가능 목표 100개에 대해 IK를 계산하고, FK 및 실제 Transform TCP와 비교한다. 이동이 끝난 뒤 위치 오차 2mm 이하, 수평 회전 오차 0.5도 이하를 초기 목표로 한다. 실제 단위 연결 후 확정한다.
3. 로봇 전체를 이동·회전해도 같은 기준 좌표 목표에서 같은 결과를 얻는지 확인한다. 집게 길이 변경에 대한 도구 오프셋도 검증한다.
4. 도달 불가 목표, 관절 제한 위반, 경계 자세, 해 전환 상황을 각각 검증한다. 잘못된 목표에서 NaN이나 갑작스러운 관절 점프가 발생하지 않아야 한다.
5. 같은 초기 조건에서 A/B 피킹을 총 100회 수행해 집기·놓기·집계를 확인한다. 화면에는 목표 TCP와 실제 TCP, 오차와 관절 값을 함께 보여준다.

6축 로봇의 위치·자세 IK는 후속 확장 후보로 남긴다. 진행할 경우 수치 해법의 수렴, 회전 오차, 특이점과 초기 자세 의존성까지 별도 범위와 일정으로 잡는다.

## 6. 외부 연동의 최소 구성

별도 C#/.NET 서버 하나와 HTTP/JSON으로 시작한다. MQTT·OPC UA·WebSocket은 첫 버전의 필수 기능으로 넣지 않는다. 자체 설비 상태와 통신 코드를 직접 연결하며 Starter 통신·신호 코드에 의존하지 않는다.

- Unity는 센서·운전 상태의 원본이다. 서버는 상태를 수신하고 이벤트를 기록하며 외부 조작 요청을 전달한다.
- 시작 값으로 초당 5회 상태 전송과 명령 조회를 사용한다. 프레임마다 네트워크 요청을 보내지 않는다.
- 명령은 시작·일시정지·정지로 제한한다. 명령 ID로 중복 실행을 방지하고 현재 상태에서 허용되지 않는 명령은 거부 사유를 반환한다.
- 화면 조작과 외부 조작은 같은 상태 전이 규칙을 사용한다.
- 통신은 비동기로 처리한다. Unity 객체 변경과 UI 반영은 메인 스레드에서 수행한다.
- 연결이 끊기면 로컬 조작을 유지한다. 재접속 시 오래된 조작 명령을 몰아서 실행하지 않는다.
- 서버에는 간단한 이벤트 파일 기록과 최근 이벤트 조회만 둔다. 별도 데이터베이스와 로그인 시스템은 나중에 필요할 때 추가한다.

이는 제안한 설계이며, 특정 API나 패키지 구성이 이미 설치·검증되었다는 의미는 아니다.

## 7. 개발 단계와 완료 조건

| 단계 | 작업 | 다음 단계로 넘어가는 조건 |

자체 IK를 포함한 예상 작업량은 주당 15~20시간 기준 약 6~8주다. 이는 기획 추정이며 모델 구성, Starter 연결과 기구학 학습 속도에 따라 조정한다. 6축 IK 확장은 이 일정에 포함하지 않는다.

## 8. 성능 검증과 최적화 과제

첫 목표는 현재 개발 PC에서 1920×1080, 물류 셀 하나의 정상 피킹과 서버 연동을 3분간 안정적으로 실행하는 것이다. 목표 프레임 예산은 60 FPS에 해당하는 16.67ms이며 CPU·GPU 시간의 중앙값과 P95를 기록한다. GPU 계측이 지원되지 않는 환경에서는 미측정으로 표시한다.

- 동일한 셀을 1·5·10개로 늘려 부하를 비교한다. 셀별 대기열 한도를 유지하고 실제 활성 상품·로봇 수, 처리량, IK 계산 시간과 호출 수를 함께 기록한다. 작은 셀에 무리하게 상품을 쌓는 조건은 사용하지 않는다.
- 동일 빌드 설정, 하드웨어, 해상도, 카메라 경로, 상품 생성 조건으로 비교한다. 로딩·워밍업 구간은 정상 운전과 분리한다.
- Development Build에서 원인을 분석하고 일반 실행 빌드에서도 동작과 성능을 확인한다. Editor 수치와 실행 빌드 수치를 섞지 않는다.
- CPU/GPU 프레임 시간, P95, GC 할당, 메모리, 드로콜, 시작·재연결 시간을 기록한다.
- 실제 병목에 따라 자체 UI 갱신, 상태 전송 빈도, 상품 생성·소멸, 충돌, 렌더링을 개선한다.
- 원본 데모의 최적화를 끈 결과를 본인의 개선 실적으로 계산하지 않는다. 본인 기능 추가 후의 동일 조건에서 전후를 비교한다.
- 개선이 필요 없거나 변경의 이득이 작다면 그 결과도 기록한다. 성능 향상률을 만들기 위해 불필요한 변경을 넣지 않는다.

## 9. 포트폴리오 제출물

1. **3~4분 영상:** 목표 조작과 FK·IK 오차 표시 → 로봇 A/B 피킹 → 적체·목표 오류와 복구 → 외부 명령·재접속 → 성능 비교.
2. **Windows 실행 빌드:** 시작 방법과 필요한 서버 실행 절차를 짧게 제공한다.
3. **README:** 해결하려는 문제, 실행 방법, 구조도, 본인 구현 범위, 에셋 출처, 측정 환경과 결과, 알려진 제한.
4. **본인 코드와 검증 근거:** FK·IK, 좌표 변환, 해 선택과 제한 처리, 상태 전이, 알람, 서버 어댑터, UI 반영과 핵심 테스트를 보여준다. 에셋 원본의 공개 범위는 라이선스에 맞춰 구분한다.

완성 후 설명 예시: “제공 모델·시각 자산을 활용하고, 설비 구동·감지·이송, 4축 SCARA의 FK·IK, 피킹 제어, 관제 동작, 고장 대응과 외부 연동을 프로젝트 코드로 구현했습니다.” 현재 완료 기능과 AI 지원 범위는 README를 따른다.
